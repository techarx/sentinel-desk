1. Project in one paragraph

Sentinel Desk is a multi-agent research copilot for a fictional bank's markets desk. It answers questions over SEC filings and a live stream of synthetic trades, and when a question needs computation it writes Python and runs it inside a gVisor (or Kata) sandbox. The point of the project is to show that untrusted, LLM-generated code and adversarial documents can run next to sensitive financial data safely, through layered controls: sandboxing, mTLS, workload identity, fine-grained authorization and guardrails. The plan has nine phases over about ten weeks; Phase 0 lays the foundations everything else builds on.

Spot instances in brief

Spot instances are AWS's spare capacity sold at a large discount (often 60–90%), in exchange for AWS being able to reclaim them with two minutes' warning. They suit short, stateless workloads such as sandbox nodes and test sessions. They suit data stores and recorded demos less well. In Terraform, an EKS managed node group becomes Spot with capacity_type = "SPOT"; listing several instance types improves the chance of getting capacity.

3. What Phase 0 built

  1. A Linux dev machine in AWS, created by Terraform, with no open inbound ports.
  2. A secure way into it from the Mac: SSH tunnelled through AWS Systems Manager (SSM).
  3. A 3-node Kubernetes cluster (kind) on that machine, with one node reserved for sandboxed code.
  4. gVisor wired into that node, plus a test proving pods there really run inside the sandbox.
  5. Argo CD, which keeps the cluster in sync with the GitHub repository (GitOps, app-of-apps).
  6. GitHub Actions CI, a Makefile that ties it all together, and ADR-001 recording the stack decisions.

5. How the SSH connection works

SSH reaches the dev machine even though port 22 is closed to the world. The trick is that no connection ever comes in: both your Mac and the dev machine connect out to AWS, and AWS joins the two connections into a tunnel.

  1. The door is locked. The security group allows no inbound traffic. Nothing on the internet, including you, can open a connection to the dev machine.
  2. The agent dials out. At boot, the SSM agent uses the instance's IAM role to open an outbound HTTPS connection to ssm.us-east-1.amazonaws.com and keeps it open. This is why the missing internet route caused TargetNotConnected: with no route out, AWS had no connection to relay through.
  3. ssh hands off to the AWS CLI. ssh sentinel-devbox reads ~/.ssh/config. Instead of dialling an IP address, its ProxyCommand runs aws ssm start-session --document-name AWS-StartSSHSession, and the Session Manager plugin carries the data.
  4. AWS checks who you are. The request is signed with your adfs credentials. SSM checks IAM to decide whether you may open a session to this instance; CloudTrail records who connected, when and to what.
  5. The tunnel is joined. SSM connects your session to the agent's already-open connection. The agent forwards bytes to localhost:22 on the machine.
  6. Normal SSH runs inside it. ssh performs its usual handshake through the tunnel and logs in with your private key, which matches the public key that user data placed in authorized_keys.

The SSH config block

Host sentinel-devbox
  HostName i-xxxxxxxxxxxxxxxxx        # the instance ID, not an IP address
  User ubuntu
  IdentityFile ~/.ssh/id_ed25519
  ProxyCommand sh -c "aws ssm start-session --region us-east-1 --target %h --document-name AWS-StartSSHSession --parameters portNumber=%p"
  ServerAliveInterval 60

make devbox-ssh-config prints this block with the real instance ID. Because the profile is adfs, either run export AWS_PROFILE=adfs in the terminal first, or add --profile adfs after start-session in the ProxyCommand.

Why this design matters. Two locks instead of one: valid AWS credentials and the SSH key. No open port to scan or attack, and every session is logged. It is the zero-trust approach the whole project is built on, and a strong interview answer to "how do you reach private servers?"

Prerequisites on the Mac

  • AWS CLI with working credentials (adfs profile).
  • Session Manager plugin: brew install --cask session-manager-plugin, or AWS's signed installer. Check with session-manager-plugin.
  • An SSH key pair (ssh-keygen -t ed25519); the public key goes in terraform.tfvars.

6. The Makefile

make runs named groups of commands called targets. make up runs whatever is defined under up:.

Why it matters

  • One command instead of fifteen. It replaces a long sequence of kind, kubectl and helm commands that must run in the right order.
  • Reproducible. The same command builds the same cluster every time, which is Phase 0's "done when" criterion.
  • Documentation that cannot go stale. The Makefile is the instructions; make help lists every target from the ## comments.
  • Shared vocabulary. The README, you, Claude and later CI all use the same commands.

How make up works

up: cluster gvisor platform argocd
TargetWhat it does

Details worth knowing

  • $$ instead of $. make uses $ for its own variables, so shell variables in recipes are written $$var.
  • .SHELLFLAGS := -eo pipefail -c. Stop at the first failing command, including failures inside pipes. -u was removed because over SSH bash reads /etc/bash.bashrc, which references the unset PS1.
  • Idempotent. Most targets check before acting, so re-running make up repairs drift instead of breaking things.

7. Argo CD and GitOps

GitOps means Git is the source of truth for the cluster. Changes are committed, not applied by hand; a controller inside the cluster applies them.

  • The root app (deploy/argocd/root-app.yaml) watches deploy/argocd/apps/. Every file there is another Argo CD app.
  • Today there is one child, platform, which watches deploy/platform/.
  • To add a component later (Postgres in Phase 1, Istio in Phase 5), add one file to deploy/argocd/apps/ and push.
  • selfHeal: true reverts manual changes to match Git; prune: true removes resources whose files were deleted.
  • "Synced / Healthy" on both apps means the cluster matches Git exactly and everything is running.

9. Why the repo is cloned on the dev machine

Argo CD exists only after the cluster does, so something has to build the cluster first. This is the classic bootstrap problem: GitOps cannot install the thing that does GitOps. make up needs these files locally where kind runs:

  • deploy/kind/cluster.yaml to create the cluster;
  • deploy/kind/install-gvisor.sh to set up gVisor;
  • deploy/platform/*.yaml for the first apply;
  • deploy/argocd/values.yaml and root-app.yaml to install Argo CD and hand over to it.

After the hand-over, Argo CD pulls everything else from GitHub itself. The clone is needed only for bootstrapping and running make commands.

11. Daily workflow and cost control

  1. Start: export AWS_PROFILE=adfs, then make devbox-start on the Mac.
  2. Edit on the Mac; commit and push.
  3. Apply on the dev machine: ssh sentinel-devbox, cd ~/sentinel-desk && git pull, then make targets.
  4. Stop: make devbox-stop at the end of every session (disk only is billed while stopped).
  • The budget alert covers everything tagged Project=sentinel-desk.
  • Bare-metal sessions: scale up, test, and destroy the same day; terminated metal instances can take 5–10 minutes to shut down. Check EC2 → Volumes afterwards for leftovers.
  • make devbox-down removes the dev machine and its VPC entirely.
